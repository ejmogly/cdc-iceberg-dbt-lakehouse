# 독립 검토: 공개 전 저장소 전체 (2026-11-20)

공개(12/4 뒤) 전에 저장소 전체를 처음 보는 눈으로 검토했습니다. 원래 11/30이던 검토를 앞당겼습니다(담당자 「검토를 앞당김」, 「독립 검토 오늘 앞당겨서 해」). 고칠 시간을 남기려는 것입니다.

- 방법: 앞 작업과 자체 평가를 모르는 검토자(에이전트) 다섯에게 범위를 하나씩 맡겼습니다. 저장소 파일만 주고 앞선 결론은 주지 않았습니다.
- 조건: 커밋 `fc047d6` 기준이고 읽기만 했습니다. docker, make(`make -n` 빼고), 네트워크, 모델 호출은 쓰지 않았습니다. git 밖 `data/`(실제 시세와 매매)와 확인용 질문, 정답은 열지 않았습니다.
- 다시 확인: 높음 전부와 중간 일부는 이 보고를 쓴 쪽이 코드와 결과 파일에서 직접 다시 봤습니다(6절). 나머지는 검토자의 보고를 옮긴 것이고 「검토자」로 표시합니다.

## 1. README만으로 따라가기

높음(여기서 막힘)

1. 필요한 파이썬 버전이 없습니다. `make setup`은 시스템 `python3`로 가상 환경을 만드는데, 의존성(`duckdb` 2.0은 3.11 이상)이 3.9에서 설치되지 않습니다. CI는 3.14입니다. README에 버전을 적고 `setup`에서 먼저 검사합니다.
2. Colima 안내대로 `brew install docker-compose`만 하면 `docker compose`(플러그인 형식)를 찾지 못합니다. 설정 한 줄(`cliPluginsExtraDirs`)이 필요하고, 준비 절이 끄기 절 뒤에 있어 순서도 맞지 않습니다.
3. 시나리오 SQL이 `now()`를 써서, 서울 날짜로 주말에 돌리면 `dbt` 테스트 `no_weekend_trade_date`가 실패하고 뒤 모델이 건너뛰어집니다. 미국에서는 금요일 낮부터 해당합니다. 시나리오에 평일 고정 시각을 넣습니다.
4. `lakehouse_refresh`의 `screen_export`가 git 밖 첫 구간 원본과 일정 정리본을 꼭 읽습니다. 원본이 없는 사람은 DAG가 30분마다 실패합니다. 원본이 없으면 건너뛰게 하거나 README에 적습니다.

중간

- `docker compose up -d`에 `--wait`가 없어 Connect, Flink, Spark가 뜨기 전에 다음 명령이 돌 수 있습니다(가이드와 보고서는 `--wait`).
- 시나리오를 넣는 명령이 README에 없고, 01 ~ 06만 넣어야 기대값이 맞는다는 말이 없습니다.
- Bronze가 찼는지 보는 조회가 `dbt build` 뒤에 있습니다. `silver.sh` 앞으로 옮기고 10 ~ 20초 기다리라고 적습니다.
- 결과 표에 화면 이야기가 많은데, 받은 사람이 화면을 띄우는 길(`make screen`, 골든 파일)과 캡처가 없습니다. 평가 기준 구간(2024-11-13 ~ 2026-11-12)을 나중에 다시 받기 어려울 수 있다는 점도 밝힙니다.
- 준비물이 「Docker 엔진」 한 줄뿐입니다. 파이썬, 메모리(VM 12GB), 디스크 60GB, aarch64에서만 확인한 점, Colima는 홈 폴더만 붙는 점을 적습니다.

낮음(검토자): 처음 보는 사람이 모를 내부 용어, Airflow 비밀번호 보는 명령, 끄기 순서, 기간 늘리기 받기가 Mac 전용인 점, 상태 날짜(11/12), `dbt build` 개수가 두 번 다르게 나옴, 표 칸 수, 폴더 그림에 빠진 폴더, 버전 표기, 공개 검사의 쓰임, `image`와 `build`를 함께 쓴 서비스의 `pull_policy`, 심볼릭 링크 seed, 그 밖의 작은 것.

## 2. 결정 기록과 코드

높음

- 0007의 환율 기준일 규칙은 11/13에 정했는데 「정할 것」으로 남았고, 규칙이 여러 곳(SQL, dbt, Gold 마트, 화면 서버)에 있습니다.

- 화면 매매를 원천으로 옮기는 일(11/18)에 결정 기록이 없습니다. 0003 「주문, 체결, 잔고는 합성」과 달라졌고, Kafka와 Bronze에 남는 그 행의 보존과 지우는 길도 정해지지 않았습니다.

## 4. 파이프라인 코드

중간

1. 화면 파일 검사가 한 번 실패하면 `lakehouse_refresh`가 스스로 풀리지 않습니다. `export_if_changed`는 검사에 실패한 새 파일로도 바꿔 쓰고, 다음 실행의 첫 태스크 `trades_to_source`는 화면 파일 검사가 실패면 멈춥니다. 그래서 Silver, dbt, 내보내기까지 가지 못합니다. 0016 영향 절의 「1분 뒤 재시도에서 통과」는 코드와 다릅니다. 실패 원인은 두 DAG가 엇갈리는 순서, 미국 종목 분할 검사 등입니다.
2. `make lake-refresh-test`를 예약 실행과 겹쳐 돌리면, 두 `silver_merge`가 한 Spark 세션에서 같은 임시 뷰 이름을 써서 Silver 구간 일부가 조용히 빠질 수 있습니다(사람이 겹쳐 돌릴 때만).
3. `window_extend`의 `wait_raw`에 `soft_fail=True`가 있어, 「앞뒤가 안 맞음(2)」이나 스크립트 오류(1)도 건너뜀이 되고 DAG 실행은 성공으로 끝납니다. Airflow 2.10.5 소스에서 `BashSensor`가 99가 아닌 실패 코드에 `AirflowFailException`을 내고, 기반 클래스가 `soft_fail`이면 이것을 건너뜀으로 바꾸는 것을 확인했습니다.
4. Silver `daily_prices` 값 검사가 Bronze의 모든 변경에 걸려, 범위 밖 행이 한 번 들어오면 원천을 고쳐도 계속 멈춥니다(키별 최신 후보에 걸어야 고친 값이 덮음).
5. 화면 매매 파일이 없는 환경에서는 `trades_verify`가 파일 없음 오류로 매번 실패합니다(`trades_to_source`는 같은 경우 통과).

낮음(검토자): 첫 스냅샷 경계의 LSN 순서, 원천 DB만 새로 만들었을 때 LSN이 작아짐, savepoint 없이 다시 보낼 때 마지막 checkpoint, 손익 장부의 매매 순서(`execution_id`만, README는 시각 먼저), `gold_incremental --full`의 plan 재사용, 유지보수가 Silver progress를 모름(2절 낮음과 같음), 기간 늘리기 Bronze 기다림이 구간 밖 키도 셈, Bronze 제출 때 비밀값의 sed 치환.

살펴봤고 문제없던 것(검토자): Silver MERGE의 가드와 삭제 표시, 증분 구간 경계와 다시 돌리기, 증분 Gold 영향 키, 시간대 변환, 손익 Spark 장부의 전량 매도와 초과 매도, Bronze 기다리기 센서, 셸 스크립트의 `set -euo pipefail`, `extend_window`의 원자적 쓰기와 지문, 적재기 upsert.

## 5. 공개해도 되는가

찾은 것은 개수와 종류만 적습니다. 위치는 공개 전에 고치면서 지웁니다.

- 회사와 조직 이름, 비밀값, 이메일, 개인 경로, 기기 이름: 추적 파일 358개와 커밋 45개(지운 줄 포함) 어디에도 없음.
- 높음 2: 개인 표기 1곳, 실제 매매처럼 보이는 시험 값 1벌(지금 저장된 실제 매매와 날짜, 가격, 환율이 모두 다름을 확인했지만 모양이 같아 둥근 값으로 바꿈).
- 중간 2: 공개에 맞지 않는 표현 몇 곳, 강의에서 나온 가이드의 2차 저작 여부(강의 쪽 확인이 이미 할 일로 열려 있음).
- 낮음 6: 커밋 시각 분포, 실제 환율 값 몇 개와 출처 표기, 실제 계좌의 흔적(값 없음), 개인 일정과 기기 사양, 예시 계좌 파일에 「가상」 표시 없음, 무시 규칙이 저장소 밖 설정에만 있음.
- `scripts/check_public.py`의 빈틈 9가지: 허용 목록 밖 파일 종류를 읽지 않음, 실제 매매 대조 없음, 바꿔 쓴 표현을 못 잡음, 이메일과 토큰 모양 검사 없음, 기록 검사가 작성자와 시세를 보지 않음, 줄을 넘는 낱말, 다른 운영체제 경로, CI에서 건너뛴 검사를 통과로 보임, 이미지 속 글자.
- git 기록: 위 높음 2와 중간 1은 지금 파일과 기록에 함께 있습니다. 공개 때 기록을 옮기는 방법(지금 할 일로 열려 있음)에서 함께 정합니다.
