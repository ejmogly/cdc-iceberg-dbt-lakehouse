# 규모 시험: 합성 매매 26만 건으로 지연, 처리량, 배치 시간, 작은 파일 (2026-11-18)

소개 페이지 8절에 「내 Mac 한 대의 작은 데이터로만 잰 것」을 가장 큰 빈칸으로 적었습니다. 그 빈칸을 줄이려고 합성 매매를 원천에 넣고, 원천 → Debezium, Kafka → Flink Bronze → Spark MERGE Silver → dbt Gold를 단계마다 쟀습니다. 끝나고 합성 매매를 모두 지워, 지움도 같은 길로 흘려 보냈습니다.

## 1. Bronze까지

체결 테이블의 숫자입니다. 주문은 같은 트랜잭션이라 거의 같고, 잔고는 트랜잭션마다 종목당 한 건이라 적습니다.

| 단계 | 매매 | 넣은 시간 | total p50 / p95 / 최대 | capture p95 | commit p95 | 모두 보이기까지 | 스냅샷 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 꾸준히 초당 20건, 3분 | 3,600 | 180.0초 | 5.7 / 10.2 / 11.1초 | 0.9초 | 9.7초 | 188.5초 | 19 |
| 몰아서 1만(500건씩) | 10,000 | 0.4초 | 10.5 / 10.7 / 10.7초 | 1.3초 | 10.0초 | 10.7초 | 2 |
| 몰아서 5만(1,000건씩) | 50,000 | 2.4초 | 4.9 / 5.8 / 5.9초 | 1.4초 | 5.0초 | 5.9초 | 1 |
| 몰아서 20만(2,000건씩) | 200,000 | 10.3초 | 6.6 / 11.3 / 11.7초 | 1.1초 | 9.4초 | 17.9초 | 2 |
| 지우기 26만(5,000건씩) | 263,650 | 1,138초 | 5.4 / 10.0 / 11.4초 | 0.7초 | 9.5초 | 1,096.7초 | 50 |

- 어느 단계든 total의 대부분은 commit(checkpoint 기다리기)이고, total p95는 checkpoint 간격(10초) 근처였습니다. 몰아 넣은 5만 건은 checkpoint 직전에 들어가 5.9초 만에 모두 보였습니다.
- 20만 건 때 Bronze가 받은 속도는 테이블마다 초당 약 11,200건(주문과 체결을 합하면 약 22,400건)이었고, 원천이 쓰기를 마친 뒤 약 8초 안에 모두 보였습니다. 원천 쓰기가 더 빨랐다면 어디서 먼저 밀리는지는 이번에 찾지 못했습니다.
- 그 순간 Connect의 CPU는 222%, 원천 PostgreSQL은 106%였고, 메모리는 Spark 2.3GiB, Airflow 1.6GiB, Kafka 1.1GiB, Connect 1.0GiB로 VM 12GiB 안이었습니다(`docker stats` 한 번).

## 2. 배치(DAG 한 번)

같은 DAG(태스크 일곱 개)를 단계마다 `airflow dags test`로 한 번 돌린 초입니다. 화면 파일 내보내기는 Gold 시세를 읽고 원본과 대조하는 일이라 매매 수와 상관없이 약 1분입니다.

| 단계 뒤(합성 매매 누계) | 전체 | Silver MERGE | `dbt build` | 그 가운데 `pnl_ledger` | 증분 Gold | 화면 내보내기 |
|---|---:|---:|---:|---:|---:|---:|
| 기준(50) | 102.1 | 8.7 | 22.6 | 0.43 | 2.4 | 59.8 |
| 꾸준히(3,650) | 105.3 | 8.6 | 22.3 | 0.35 | 1.8 | 63.2 |
| 1만(13,650) | 107.6 | 10.8 | 24.0 | 0.69 | 2.0 | 62.8 |
| 5만(63,650) | 121.4 | 16.7 | 28.1 | 4.23 | 2.7 | 64.3 |
| 20만(263,650) | 186.4 | 34.1 | 77.5 | 33.90 | 5.3 | 63.1 |
| 지운 뒤(0) | 142.5 | 51.3 | 17.4 | 0.23 | 3.8 | 61.4 |
| 압축 뒤 마지막(0) | 179.5 | 73.3 | 20.3 | 0.26 | 10.6 | 65.3 |

- 손익 장부는 계산 단위(계좌 x 종목)마다 매매를 배열로 모아 한 줄씩 접고, 접을 때마다 그 줄 뒤 상태를 배열에 붙입니다([`dbt/models/pnl/pnl_ledger.sql`](../../dbt/models/pnl/pnl_ledger.sql)). 종목 19개에 매매가 고루 들어가 한 단위에 약 1만 4천 건이 됐을 때 시간이 매매 수보다 빨리 늘었습니다(4.1배에 8.0배). 붙일 때마다 배열을 새로 만드는 비용이 쌓인 것으로 봅니다(해석, 실행 계획은 보지 않음). 실제 계좌의 한 종목 매매가 이만큼 되는 일은 드뭅니다.
- Silver MERGE는 지운 뒤와 마지막에 더 느려졌습니다. 바뀐 것을 고르는 1단계가 Bronze 이력 전체를 매번 펼치기 때문이고, Bronze 체결이 55행에서 727,355행(넣기와 지우기, 아래 견주기 포함)이 됐습니다. 마지막 실행은 바뀐 것이 없었는데도 73.3초였습니다.

## 3. 지우기와 원래대로

합성 매매를 5,000건씩 지웠습니다(체결 → 주문, 마지막에 잔고 19건). 지움 이벤트도 total p95 10.0초로 Bronze에 보였고, Silver는 체결 263,650건에 지움 표시를 남겼습니다(체결은 REPLICA IDENTITY FULL이라 지우기 전 값까지). Gold의 `fct_execution`과 손익 마트에서 `A-LOAD`는 0행이 됐습니다.

시험 전에 Gold를 읽어 둔 지문 다섯 개를 지운 뒤 다시 읽어 견줬습니다. 시세 9,472행, 환율 488일, 체결 5행, 손익 마트 3행, 손익 기준일이 모두 글자째 같았고, 마지막 DAG 뒤에도 같았습니다. 화면 매매 대조(`trades_verify`)는 단계마다 1/1이었고, 화면 파일은 내용이 같아 한 번도 바뀌지 않았습니다.

## 4. 원천에서 먼저 막힌 곳

지우기 26만 건이 19분(1,138초) 걸렸습니다. Bronze는 그동안 초당 약 240건을 p95 10초 안에 받았으니, 느린 쪽은 원천의 지우기 자체였습니다. 원천의 체결 테이블에는 기본 키(`execution_id`) 인덱스만 있고, 외래 키를 거는 칸 `order_id`에는 인덱스가 없습니다. 그래서 주문 한 건을 지울 때마다 그 주문을 가리키는 체결이 있는지 체결 테이블을 처음부터 훑습니다.

| 5만 건 지우기 | 걸린 시간 |
|---|---:|
| 인덱스 없이(지금 구조) | 36.6초 |
| `order_id` 임시 인덱스를 둔 뒤 | 0.62초 |

임시 인덱스는 잰 뒤 바로 지웠고, 같은 날 담당자가 이 인덱스를 원천 구조에 넣기로 정했습니다([0012](../decisions/0012-executions-order-id-index.md)). 넣은 뒤 5만 건 지우기는 세 번 0.47, 0.49, 0.43초였습니다. 넣을 때는 이 검사가 체결 쪽에서 주문의 기본 키를 찾으므로 느리지 않았습니다. 5만 건 넣기는 2.4 ~ 2.5초인 회차와 32 ~ 36초인 회차로 갈렸습니다(여섯 번 가운데 셋). 인덱스가 있든 없든, 지운 행을 정리(`VACUUM`)한 뒤에도 느린 회차가 있었고, 대기 종류를 찍은 회차는 빨라 원인을 찾지 못했습니다.

## 5. 작은 파일과 압축

꾸준히 넣은 3분 동안 Bronze 테이블마다 checkpoint마다 데이터 파일이 하나씩(19개, 그때 테이블의 파일 평균 약 11KB), 시험 전체로 Bronze 체결에 데이터 파일 98개가 생겼습니다. Flink 작업을 savepoint로 멈추고 유지보수 실행기([`sql/maintenance/maintain.py`](../../sql/maintenance/maintain.py))로 Bronze 체결을 압축한 뒤, Silver 체결 MERGE만(바뀐 것 없음) 세 번씩 쟀습니다.

| Bronze 체결 파일 | Silver 체결 MERGE(세 번) |
|---|---|
| 작은 파일 98개 | 29.8, 30.1, 29.1초 |
| 하나로 압축(27MB) | 54.1, 50.2, 49.2초 |
| 같은 파일에 읽기 조각 4MB 설정 | 52.3, 53.2, 50.9초 |
| 4MB 목표로 다시 압축(7개) | 32.4, 28.8, 30.4초 |

- 압축 전후로 행 수(727,355)와 합계가 같았습니다.
- 하나로 합친 파일은 Spark가 읽기 작업 하나로 727,355행을 읽었고, 압축하지 않은 Bronze 주문(파일 103개)은 작업 26개로 나눠 읽었습니다(Spark 실행 기록). 이 크기에서는 파일 수보다, JSON 풀기를 코어 여럿에 나누는지가 시간을 정한 것으로 봅니다(해석). 파일 하나에 Parquet 행 그룹이 하나라 읽기 조각 설정만으로는 나뉘지 않았습니다.
- 지금 Bronze 체결은 4MB 목표의 7개 파일입니다. 테이블 설정은 바꾸지 않았습니다.

## 6. 해석과 한계

- 이 숫자는 VM 하나, 연결 하나, 단계마다 한 번의 결과입니다. 클라우드, 여러 작업자, 큰 Kafka 묶음에서도 같은 순서로 막힌다고 말할 수는 없습니다.
- CDC와 Bronze는 이번 크기에서 한계에 닿지 않았고, 지연은 checkpoint 간격이 정했습니다. 간격을 줄이면 지연이 줄고 작은 파일과 빈 commit이 늘어납니다(11/12 보고서 2절).
- 배치 쪽에서는 Silver가 Bronze 이력 전체를 읽는 것과 손익 장부의 배열 접기가 매매 수보다 빨리 느려졌습니다.
- 남은 흔적: Bronze 주문과 체결에 시험 이벤트 약 73만 건, Silver 주문과 체결에 지움 표시 각 263,658건(화면 시험 8건 포함)이 있습니다. Gold와 화면에는 영향이 없고, Silver 증분 읽기(7절) 뒤에는 DAG 시간에도 영향이 없습니다(전체 읽기 `--full`, `--compare`만 이력만큼 걸림).

## 7. 고친 뒤: Silver 증분 읽기 (같은 날)

담당자가 「Silver 증분 읽기로」를 골랐습니다([0011](../decisions/0011-silver-incremental-read.md)). Silver 실행기([`sql/silver/run.py`](../../sql/silver/run.py))가 테이블마다 마지막으로 읽은 Bronze 스냅샷을 남기고, 다음에는 그 뒤에 더해진 행만 Iceberg 변경 뷰로 읽습니다. `1_incoming.sql`, `2_merge.sql`은 그대로이고, Bronze를 읽는 한 곳만 바꿔 끼웁니다. DAG의 `silver_merge`가 이 실행기를 씁니다.

| 경우 | Silver 시간 | 전체 재계산과 비교 |
|---|---:|---|
| 첫 실행(전체 읽기, Bronze 주문과 체결 각 약 73만 행) | MERGE 61초 | 다섯 테이블 0 / 0 |
| 바뀐 것 없음(빈 스냅샷만) | 1.2초(MERGE 건너뜀) | 0 / 0 |
| 매매 50건 | 테이블마다 1 ~ 1.5초 | 0 / 0 |
| 실행 사이에 Bronze 주문 압축(104 → 5개) 뒤 매매 30건 | 새 행 30개만 읽음 | 0 / 0 |
| MERGE 뒤 progress 저장 전에 멈추고 다시 | 같은 구간을 다시 읽음 | 0 / 0 |
| progress 스냅샷이 없음(만료 흉내) | 그 테이블만 전체 읽기 | 0 / 0 |
| 합성 매매 100건 지우기 | 지움 표시로 반영 | 0 / 0 |

Airflow DAG(`airflow dags test`)에서는 바뀐 것이 없을 때 `silver_merge` 73.3초 → 1.6초, DAG 전체 179.5초 → 110.6초였습니다. 시험 매매 파일(체결 8건 넣기)은 `silver_merge` 6.2초, 되돌리기(8건 지우기)는 3.7초였고, Gold 체결 9/9, 손익 마트 4/4종목, 되돌린 뒤 1/1이 같았습니다. 증분 Gold도 매번 정답지와 0 / 0이었습니다. 이제 DAG 한 번에서 가장 긴 일은 화면 파일 내보내기(약 1분)입니다.

증분에서는 `1_incoming.sql`의 검사가 구간 안의 행에만 걸립니다. 구간을 넘는 검사는 `run.py --compare`와 `--full`로 봅니다.
