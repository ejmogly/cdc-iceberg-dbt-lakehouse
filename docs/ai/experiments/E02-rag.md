# E02. 그때 무슨 일이 있었나 (RAG)

> 상태: 확인용 한 번 끝(2026-11-20, 5절). 규칙 지표는 모두 통과, 판정 모델 지표는 사람 확인 없는 참고값. 개발은 2026-11-17 시작([F 화면](../F-screen.md) 7단계). 0단계 조사를 2026-11-06에 했고(3절), 결과에 따라 가설과 범위를 고쳤습니다.
> 평가 기준을 확정한 날: 2026-11-13 13:03, 개발 전. F 화면의 평가 기준과 함께 지문으로 고정하고 2026-11-16에 커밋했습니다(`6f4064b`, 대조는 `eval/f_screen/lock.py --verify`). 일정 출처는 11/13에 정했습니다(F 화면 6절 5번).

## 1. 문제

보유 기간에 크게 움직인 날, 그날 무슨 일이 있었는지 찾으려면 여러 곳을 뒤져야 합니다. 찾았더라도 "그래서 움직였다"고 믿기 쉽습니다. 사용자는 **그날 함께 나타난 일과 그 출처**를 한 번에 보고 싶어 합니다.

## 2. 가설

기준선은 "그 종목 표시가 붙은 그날 기사를 최신순으로 5개"입니다. 아래 순서로 하나씩 더해 보고, 값을 못 하는 단계는 버립니다.

| 번호 | 바꾸는 것 | 재는 것 | 기대하는 차이 |
|---|---|---|---|
| H1 | 날짜로 거른 창의 전체 기사(약 400건)에서 자산군 주제로 낱말 검색(BM25) | recall@5 | 기준선보다 0.15 이상 높음 |
| H2 | 의미 검색(임베딩)을 더함 | recall@5 | H1보다 0.05 이상 높아야 추가 부품의 값을 함. 회사 이름에 걸린 오탐을 줄이는지가 핵심 |
| H3 | 일정 표(금리 결정, 물가 지표)와 같은 날 다른 자산의 움직임을 근거에 더함 | 근거 충실도, 답할 수 있는 날의 비율 | 충실도를 지키면서 기사가 적은 날도 답함 |
| H4 | 모델을 작은 것으로 바꿈 | 근거 충실도, 인과 표현, 비용 | 품질 통과선을 지키면 작은 모델을 씀 |

H1, H2는 처음에 "날짜와 종목으로 거른 뒤 검색"이었습니다. 0단계에서 ETF 표시 기사가 하루 중앙값 0건으로 나와, 미리 정한 규칙대로 그 형태는 버리고 검색 대상을 창의 전체 기사로 바꿨습니다.

## 3. 평가 기준 (개발 전에 확정)

### 범위

| 칸 | 정한 것 |

| 큰 움직임 | 하루 등락의 절댓값이 최근 60일 표준편차의 2배를 넘은 날. 등락은 단순 수익률(종가 / 전날 종가 - 1, 수정한 가격), 표준편차는 그날을 뺀 앞 60거래일 수익률의 표본 표준편차(n - 1로 나눔). `eval/e02_rag/step0_survey.py`의 `big_move_days`와 같음 |

### 평가셋

| 묶음 | 수 | 확인하는 것 |
|---|---|---|
| 큰 움직임 날 | 24 | 검색과 답의 품질. 자산군이 고르게, 개별 기업을 포함하고, 일정이 있는 날과 없는 날을 섞음 |
| 평범한 날 | 8 | 없는 사건을 지어내지 않는지 |
| 근거를 뺀 날 | 8 | 모른다고 답하는지 |

- 날짜는 `eval/e02_rag/pick_dates.py`가 시드 20261113으로 고르고 `eval/e02_rag/eval_dates.json`에 둡니다(2026-11-13). 기사 수는 고르는 데 쓰지 않습니다. 자산군은 `loaders/instruments.csv`의 `group` 칸이고, 40개는 서로 2거래일 이상 떨어져 검색 창이 겹치지 않습니다.
- **평범한 날:** 하루 등락의 절댓값이 같은 표준편차의 0.5배 이하이고, 앞뒤 거래일도 큰 움직임이 아닌 날. 기대 답은 「그날 크게 움직이지 않았다」고 밝히고, 있는 근거만 전하며 사건을 지어내지 않는 것입니다.
- **근거를 뺀 날:** 큰 움직임 날 가운데 위 24개와 겹치지 않는 날. 평가할 때 그날의 기사, 일정, 같은 날 다른 자산의 움직임을 **모두** 검색 대상에서 뺍니다. 기대 답은 「찾지 못했습니다」입니다.
- **일정 비율:** 일정 데이터를 받기 전에 날짜를 골라, 일정이 있는 날과 없는 날을 섞으라는 조건은 지키지 못했습니다. 일정을 받은 뒤 큰 움직임 24개 가운데 일정이 있는 날의 수를 세어 결과에 밝히고, 치우쳐도 **다시 고르지 않습니다**(결과를 본 뒤 평가셋을 바꾸지 않으려고 미리 정함).
- 40개를 **개발용 24개와 확인용 16개**로 나눕니다. 확인용은 마지막 판에 한 번만 돌립니다. market-watch에서 개발용 검출률 91.7%가 확인용에서는 66.7%였던 경험 때문입니다.
- 날짜는 실제 시세로 뽑습니다. 그래서 평가셋은 시세와 기사를 받은 뒤에 만듭니다(0단계 다음).
- 재배포 금지 때문에 저장소에는 **날짜, 종목, 기사 번호, 관련 표시만** 둡니다. 제목과 요약은 `data/raw/`(git 제외)에 둡니다.

**관련 기사의 뜻:** 그날 그 종목이나 자산군에 함께 나타난 일을 사실로 담은 기사입니다. 움직임의 원인인지는 묻지 않습니다.

**관련 표시를 만드는 법.** 사람이 다 보면 800건이 넘으므로 줄입니다.

1. 기준선과 각 판의 상위 5건을 합친 기사만 표시합니다(풀링). 어느 판도 찾지 못한 관련 기사는 세지 못하므로, recall은 판끼리 비교하는 값입니다.
2. 판정 모델이 먼저 표시합니다.
3. 사람은 표본 100건만 예, 아니오로 누릅니다. **30분 안**에 끝나고, 값은 페이지에 저장되는 것만 인정합니다.
4. 판정 모델과 사람의 일치도(카파)가 0.7 이상일 때만 판정 모델의 점수를 씁니다. 못 넘으면 판정 기준을 고치거나 사람 표본을 늘립니다.

E01에서 69칸을 손으로 검산하게 했더니 값이 남지 않았습니다. 사람 몫은 작게 잡고, 기록은 클릭으로 저절로 남깁니다.

### 미리 예상하는 실패

| 실패 | 어디서 드러나나 | 대응 후보 |
|---|---|---|
| 종목 표시 기사가 너무 적어 검색이 필요 없음 | 0단계에서 확인 | 검색 대상을 창의 전체 기사로 바꿈 |
| ETF에 기사가 거의 안 붙음 | 0단계에서 확인 | 주제어 검색, 일정 표, 다른 자산의 움직임 |
| 주제어가 회사 이름이나 보도자료에 걸림 | recall@5, 근거 충실도 | 의미 검색(H2), 출처별 가중, 주제어 다듬기 |
| 의견 글과 보도자료뿐이라 그날의 사건이 없음 | 답할 수 있는 날의 비율 | 일정 표와 다른 자산의 움직임으로 답하고, 기사는 찾지 못했다고 말함 |
| 의견 글의 "왜 내렸나" 제목을 원인처럼 옮김 | 인과 표현 | 출처를 밝혀 따옴표로만 전함 |
| GDELT API가 막힘(11/06 두 번, 원인 미확인) | 0단계에서 확인 | 1판에서 쓰지 않음. 나중에 원본 파일이나 BigQuery |
| 답에 "때문에"가 섞이거나 기사 제목의 인과 표현을 그대로 옮김 | 인과 표현 | 규칙 검사 뒤 다시 쓰기, 제목은 따옴표로만 |
| 근거가 없어도 그럴듯하게 지어냄 | 모름 응답, 근거 충실도 | 근거 없음 분기를 코드로 처리 |
| 판정 모델이 관대해 점수가 부풀음 | 카파 | 판정 기준을 고치고 사람 표본 늘림 |
| 영어 기사와 한국어 답 사이에서 뜻이 바뀜 | 근거 충실도 | 기사 말은 원문을 함께 보임 |
| `claude -p` 호출 시간이 들쭉날쭉해 지연을 믿기 어려움 | 지연 | 빈 호출 기준으로 빼고, 나중에 API로 다시 잼 |

## 4. 개발

순서는 다음과 같습니다. 날짜와 사람 몫은 [F 화면](../F-screen.md) 7절 7단계에 있습니다.

1. 일정 데이터 출처 결정. 그 뒤 평가 기준을 커밋합니다. (끝남, 11/13 결정, 11/16 커밋)
2. 전체 기사와 일정 수집, 평가셋과 관련 표시. (기사 11/13, 일정 11/17, 관련 표시 풀 11/17. 판정 모델 표시와 사람 표본은 다음)
3. 기준선을 먼저 돌려 점수를 남기고, H1부터 하나씩 더합니다.
4. 마지막 판을 확인용 16개에 한 번 돌립니다.

**일정(11/17).** `loaders/schedule_events.py`. FOMC(연준 일정 페이지) 17개, CPI(FRED release 10) 25개, 고용 보고서(FRED release 50) 24개(2024-11-13 ~ 2026-12-31). 국내 일정은 1판에서 받지 않습니다(국내 종목을 뺌). 검색 도구는 일정을 **전날 장 마감부터 그날 장 마감 전까지** 발표된 것으로 고릅니다. 기사 창(다음 날 장 시작 전까지)보다 짧게 잡은 것은, 그날 장이 끝난 뒤 발표된 일정(다음 날 08:30 CPI 등)은 그날 움직임과 같은 날에 나타난 일이 아니기 때문입니다. 기사 창 안이므로 「인용 유효」(검색 창 안) 정의와 어긋나지 않습니다. 휴장일 발표(2026-04-03 성금요일 고용 보고서)는 다음 거래일 쪽에 듭니다.

**검색 판(11/17).** `ai/news_search.py`.

| 판 | 하는 일 |
|---|---|
| 기준선 | 창 안에서 그 종목 표시 기사를 최신순으로 5건 |
| H1 | BM25(k1 1.2, b 0.75, 제목은 두 번 셈). ETF는 창의 전체 기사에서 자산군 주제어로(0단계 `step0_topics.py`의 주제어를 낱말로 풀고 SPY, QQQ, IBIT을 더함), 개별 기업은 표시 기사 안에서 회사 이름과 종목 코드로. 붙임 낱말(s&p, small-cap, trillion-dollar)은 한 낱말로 셈 |

한 날을 손으로 끝까지 본 것(개발 날짜):

- GLD 2025-09-02: 창 549건(GlobeNewswire 304, The Motley Fool 141, Benzinga 80, Investing.com 24), GLD 표시 0건. 금 주제어에 걸린 4건은 모두 광산 회사 보도자료였고 금 시장 이야기는 없었습니다. 0단계의 「출처 치우침」이 그대로입니다.
- TSLA 2026-04-02: 창이 성금요일 휴장을 건너 2026-04-06 09:30까지라 733건, TSLA 표시 31건. 기준선(최신순)은 주말의 의견 글 5건을 골랐고, H1은 1분기 인도량 기사 4건을 골랐습니다.
- UUP 2025-04-10: 붙임 낱말을 나눠 세던 첫 판이 「Trillion-Dollar」를 「dollar」로 잡아, 붙임 낱말을 한 낱말로 세게 고쳤습니다(평가셋을 보기 전 낱말 나누기 규칙 하나).

**관련 표시 풀(11/17).** `eval/e02_rag/pool.py` → `eval/e02_rag/pool_dev.json`(기사 번호만). 개발용 큰 움직임 날 14개에서 기준선과 H1의 상위 5건을 합쳐 80건입니다(두 판이 함께 고른 것 5건). ETF 날은 표시 기사가 거의 없어 기준선이 0 ~ 1건입니다. 풀이 80건이라 사람 표본은 100건이 아니라 개발 풀 80건 전부입니다. 풀을 훑어보니 H1에 회사 이름(「Dollar General」), 상 이름(「Wins Gold」), 배당 「yield」가 걸린 기사가 섞입니다. 3절 「미리 예상하는 실패」의 「주제어가 회사 이름이나 보도자료에 걸림」이고 대응 후보는 H2입니다. 관련 표시를 받기 전에 H1을 더 고치지 않습니다(개발 날짜에 맞춰 주제어를 고르는 일을 막으려고).

**판정 모델 표시(11/17).** `eval/e02_rag/judge.py`, 판정 기준 `ai/prompts/e02_judge_rel_v1.txt`(3절 「관련 기사의 뜻」을 종목과 ETF별 시장으로 풀어 씀. 이름만 겹침, 시장을 말하지 않는 한 회사의 보도자료, 그 창의 사실이 없는 일반론은 아니오). 날마다 풀의 기사를 한 번에 묶어 부릅니다. 개발 풀 80건 가운데 25건을 관련으로 표시했습니다(14번 호출, $0.15). 표시는 `eval/e02_rag/labels_dev.json`의 `judge`(기사 번호와 true, false), 이유는 `data/generated/e02/`(git 제외)입니다. 같은 날(TSLA 2026-04-02)을 두 번 부르니 10건 가운데 1건(SpaceX 상장 기사)의 표시가 바뀌었습니다. 판정 모델이 경계에 있는 기사에서 흔들린다는 뜻이라, 카파와 함께 결과에 밝힙니다. 11/20 근거 질문 인용 정답([F 화면](../F-screen.md) 7절)을 만들며 한 풀(NVDA 2025-04-09, 8건)을 일곱 번 불러 보니 1건이 일곱 번 가운데 4번 관련이었고, 11/18에 한 번 부른 결과와는 2건이 달랐습니다. 인용 정답은 세 번 다수결로 고정했고, 이 문서의 관련 표시(개발 풀 80건)는 한 번 부른 값 그대로입니다.

**사람 표본(11/17 준비, 11/20 빼기로 함).** `eval/e02_rag/sample_tab.py`가 진행판(비공개)에 「관련 표시」 탭을 넣습니다. 개발 풀 80건 전부를 날짜 순으로 묶고, 날 안에서는 시드로 섞어 어느 판이 골랐는지 숨기고, 판정 모델의 표시는 보이지 않습니다. 판정 기준과 같은 기준을 한국어로 탭 머리에 둡니다. 누른 값은 진행판 db(`e02_labels`)에 저장되고, `eval/e02_rag/kappa.py --db`가 받아 `labels_dev.json`의 `human`에 옮겨 카파를 셉니다(자체 시험 4/4, 가짜 사람 표시로 끝까지 한 번 돌림). 11/20 담당자가 사람 표본을 빼기로 정했습니다(「3안, 빼고 밝히기」). 판정 모델과 같은 모델이 대신 표시하는 길은 같은 모델끼리 맞춰 보는 셈이라 쓰지 않았습니다. 그래서 3절의 조건(카파 0.7 이상일 때만 판정 모델 점수를 씀)을 채우지 못하고, 판정 모델로 잰 값(recall@5, 근거 충실도, 인과 표현의 판정 모델 쪽)은 사람 확인을 거치지 않은 참고값으로 적습니다(5절). 탭에 남은 한 건은 저장이 되는지 보려고 누른 것이라 쓰지 않습니다.

**답 쓰기 판 1(11/17).** `ai/e02_answer.py`, 답 규칙 `ai/prompts/e02_write_v2.txt`, 실행기 `eval/e02_rag/run.py`.

- 답은 두 부분입니다. 날짜, 하루 등락률, 앞 60거래일 표준편차의 몇 배인지, 큰 움직임인지는 코드가 씁니다(숫자 일치). 기사 요약은 모델이 1 ~ 4문장으로, 문장마다 기사 번호를 붙여 기사가 전한 사실만 씁니다. 일정은 이 판의 근거에 넣지 않습니다(H3).
- 모델 글은 코드가 검사합니다: 인용 번호(1 ~ 5), 인과 표현(채점기 규칙과 더 엄한 낱말), 숫자(인용한 기사 글에 있는 숫자만, 「Q1」을 「1분기」로 옮긴 것은 인정). 걸리면 한 번 다시 쓰고, 그래도 걸리면 코드 문구로 숨깁니다. 근거가 없으면 모델을 부르지 않고 「찾지 못했습니다」.
- 한 날을 손으로 볼 때 고친 것 둘: 답 규칙 v1은 「360,000」을 「36만」으로 옮겨 숫자 검사에 걸렸고(v2: 기사의 숫자를 그대로), 「마침표 뒤 빈칸이 없으면 문장을 나눔」 규칙이 소수점까지 나눠 「8.8」을 8과 8로 읽었습니다. 둘째는 6단계 `ai/qa.py`의 금지 표현 검사에도 있던 버그라 함께 고쳤습니다(마침표 뒤가 숫자면 나누지 않음, 갈래 시험 27/27과 자체 시험 13/13 그대로).
