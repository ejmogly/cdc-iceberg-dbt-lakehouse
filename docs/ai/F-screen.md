[AI 트랙 계획](README.md)의 F(화면)입니다. 11/06 구상 페이지에 가짜 숫자로 그린 「내 투자 돌아보기」를 **실제 시세와 환율로** 만들고, 이 저장소를 소개하는 페이지로 마무리합니다.
화면은 내 컴퓨터에서만 돌립니다. 실제 시세와 기사는 재배포가 금지라 저장소와 공개 페이지에 넣지 않습니다(2절 「실제 시세 보호」).

## 1. 문제

나눠서 사고판 매매의 결과를 원화로 이해하려면 계산(E01), 범위(E03), 묻고 답하기(E04)를 명령줄에서 따로 돌려야 합니다. 사용자는 **매매를 넣으면 한 화면에서** 손익과 그 출처(가격, 환율), 보유 기간에 함께 나타난 일, 앞으로의 범위를 보고 싶어 합니다.
그리고 이 저장소를 처음 보는 사람은 README와 보고서만으로는 무엇이 돌아가는지 한눈에 보기 어렵습니다. 화면과 소개 페이지가 그 빈칸을 채웁니다.

## 2. 만들 것

### 화면의 칸

화면은 한 번에 **한 종목**을 봅니다(구상 페이지와 같음). 여러 종목을 합친 화면은 다음 판입니다.

| 번호 | 칸 | 보여 주는 것 | 계산하는 곳 | E01 골든이 덮나 |
|---|---|---|---|---|
| 1 | 매매 입력 | 종목(19개), 매매 줄(날짜, 매수와 매도, 수량, 체결가, 환율), 기준일. 체결가와 환율을 비우면 그날 종가와 매매기준율 | 화면 | |
| 2 | 요약 카드 | 원화 손익(실현과 평가), 달러 손익, 같은 날 같은 돈을 SPY에 넣었을 때와 차이, 최대 낙폭(원, E01 R14), 연 환산 수익률 | 손익 SQL(`pnl_position`, `pnl_irr`) | 덮음 |
| 3 | 가격과 내 매매 | 가격 흐름, 평균 단가 선, 매수와 매도 표시, 큰 움직임 표시 | 손익 SQL(`pnl_ledger`)과 시세. 큰 움직임은 E02의 정의(하루 등락의 절댓값이 최근 60일 표준편차의 2배 초과) | 평균 단가만 덮음. 큰 움직임은 새 계산 |
| 4 | 누적 손익 | 내 매매와 SPY 기준선의 누적 손익(원화) | 내 매매는 `pnl_daily`. SPY 선은 새로 짬(`pnl_daily`에 SPY 줄이 없음) | 끝 값만 덮음. 4절 「새로 짠 계산」으로 대조 |
| 5 | 원화 수익 나누기 | 가격 효과, 환율 효과, 교차 효과 | 손익 SQL | 덮음(E01 항등식) |
| 6 | 매도별 손익 | 매도 한 건마다 수량, 가격, 평균 단가, 원화 손익 | 손익 SQL(`pnl_sells`) | 덮음 |
| 7 | 그때 무슨 일이 | 보유 기간의 큰 움직임 날과, 같은 날의 기사와 일정. 출처를 인용하고 「같은 날 나타난 일」까지만 말함. 국내 2종목은 「국내 종목은 기사 근거가 없습니다(다음 판)」라는 고정 문구 | 검색(E02) | |
| 8 | 앞으로의 범위 | 그 종목의 20일 80% 범위와, 그 범위가 그 종목의 지난날에 몇 번 맞았는지(n과 함께) | 새 계산(E03 기준선 「최근」) | |
| 9 | 묻고 답하기 | 질문을 받아 도구(손익, 시세, 환율, 기간 통계, 범위, 검색)를 불러 답함. 숫자는 도구 결과에서만 옮기고 숫자 추적으로 검사 | 에이전트(새 판) | |
| 10 | 파이프라인 상태 | 데이터를 마지막으로 내보낸 때, 원천과 내보낸 행 수, 기간, 빈 거래일, 환율이 없는 날 수, 손익 SQL 골든 30/30. 하나라도 실패하면 숫자 대신 실패 항목을 보임 | 내보내기 검사 | |

**8번 칸(앞으로의 범위)은 E03의 결론을 넘지 않습니다.**

- 범위는 E03 확인 구간 전체에서 pinball loss가 가장 작았던 기준선 「최근 20일 변동성」으로 냅니다(「섞음」과 거의 같고, 2026년을 빼면 「섞음」이 근소하게 작음). 단순 계산이라고 밝힙니다.
- 대상은 E03과 같이 **현지 통화 가격의 수익률**입니다. 환율과 분배금은 넣지 않습니다. 원화 범위가 아닙니다.
- 적중률은 그 종목의 지난날에서 겹치지 않는 20일 창으로 세고, **n을 함께** 보입니다(2년 데이터의 마지막 날 기준 n = 23). 20일 적중률이 70 ~ 90% 밖이면 화면에 알립니다(E03 「참고 적중률」 규칙). 2년으로는 판정에 모자라 참고로만 보입니다.
- n이 작으면 70 ~ 90% 안에 들 수 있는 값이 몇 개뿐이라 알림이 쉽게 켜집니다(n = 11이면 8/11, 9/11만 안). 그래서 n이 20보다 작으면 알림 대신 「표본이 적어(n) 적중률로 판단하기 어렵습니다」라고 씁니다.
- 이 종목에서 「최근」이 다른 기준선보다 낫다는 것은 재지 않았습니다. E03은 코스피 하나에서 나온 결과이고 다른 자산으로 일반화하지 않습니다.
- 「비슷했던 때」 사례와 코스피 시장 참고는 이번 판에서 넣지 않습니다. 넣으려면 E03 3절의 독립 횟수, 문장, 조회 지연 지표를 이 문서로 옮겨야 합니다.

**9번 칸(묻고 답하기)은 E04의 통과한 판이 아닙니다.** E04 H1 판 3은 확인용에서 숫자 18/18, 틀린 숫자 0이었지만 모름과 되묻기 2/4, 금지 표현 2건, 숫자 추적 19/20(채점기 한계로 봄)으로 통과하지 못했습니다. 그래서 그대로 붙이지 않고 새 판을 만들어 이 문서의 평가셋으로 다시 판정합니다. E04 결과는 물려받지 않습니다.

| 새 판에서 바꾸는 것 | 근거 |
|---|---|
| 「모름」을 코드가 정함. 분류가 모름이거나 도구 결과에 근거가 0건이면 코드가 상태를 정함 | E04 다음 가설 1 |
| 금지 표현을 답 뒤에 코드로 검사하고, 걸리면 한 번 다시 쓰게 함 | E04 다음 가설 2 |
| 범위 도구를 「최근 20일 변동성」 계산으로 바꾸고, 답 틀을 「범위, n, 과거 적중률」로 새로 씀. 「비슷했던 12번」 문장은 쓰지 않음 | E03 결론. 지금 프롬프트(`ai/prompts/rules_v3.txt`)와 도구(`similar_periods`)는 비슷했던 때를 전망 근거로 씀 |
| 검색 도구는 E02 판이 정해진 뒤 붙임. 그 전에는 그날 일을 묻는 질문에 모른다고 답함 | 일정 순서(5절) |
| 채점기가 도구 결과의 글(기사 제목 등) 속 숫자도 보게 고침. 고친 뒤 채점기 자체 시험(`--selftest`)을 다시 돌리고, 평가 기준 커밋 전에 끝냄 | E04 다음 가설 3. 실제 데이터에서는 모델이 기억으로 숫자를 말할 수 있어(E04가 가짜 세계를 쓴 이유), 숫자 추적이 채점기 한계로 흔들리면 안 됨 |

매수나 매도를 추천하는 칸은 만들지 않습니다. 데이터 사이의 관계는 「같이 움직였다」까지만 말합니다.

도구 층에서 바꾸는 일곱 가지:

1. 「내 계좌」는 화면에 넣은 매매, 「오늘」은 기준일입니다. 국내 시세는 다음 날 오후에 들어오므로 국내 종목의 마지막 날은 하루 늦을 수 있습니다(E03 L4와 같은 이유).
2. 기사는 E02의 검색 창(거래일 t의 전날 장 마감부터 t 다음 날 장 시작 전까지, 미국 동부 시각)으로 고릅니다. 지금은 UTC 날짜로 고릅니다.
3. 도구의 날짜 해석(휴장일, 「지난주」)은 시장마다 다른 달력을 씁니다. 손익 SQL에 넣는 달력은 지금처럼 시세와 환율 날짜를 합친 하나입니다(E01 전제. 시장별로 나누면 환율만 움직인 날이 빠져 R14 낙폭이 달라짐).
4. 소수 수량은 말없이 자르지 않습니다. 그 줄을 계산에서 빼고 `FRACTIONAL_QTY` 경고를 냅니다(E01 R16: 소수점 매매는 범위 밖, 손익 SQL의 수량은 정수).
5. 이름이 같은데 정의가 다른 값은 나눠 부릅니다. 「최대 낙폭」은 요약 카드의 원 단위 손익 기준(E01 R14)과 기간 통계의 가격 기준 %로, 「큰 움직임」은 3번 칸의 E02 정의(60일 표준편차의 2배)와 기간 통계의 「가장 큰 하루 움직임」으로 나눕니다.
6. 손익 엔진의 기준 종목 기본값(`bench="BENCH"`, 가짜 세계 이름)을 실제 데이터에서는 SPY로 넘깁니다.
7. 실제 데이터로 부른 모델 호출의 장부와 실행 기록은 `data/generated/`에 씁니다. 지금은 git이 추적하는 `eval/e04_agent/runs/`에 쓰고, 실패한 호출은 모델 글을 500자까지 남깁니다.

### 실제 시세 보호

- 실제 데이터로 만든 정답, 실행 기록(도구 결과 포함), DuckDB 파일, 매매 저장 파일은 모두 `data/generated/`(git 제외)에 둡니다. `.gitignore`에 `*.duckdb`도 더합니다.
- 저장소에는 사례와 질문의 정의(종목, 날짜, 수량, 질문 글)와 정답 파일의 sha256만 둡니다(E03의 `criteria_lock.json` 방식). E04처럼 도구 결과가 든 실행 기록을 커밋하지 않습니다.
- 공개 전 검사(`scripts/check_public.py`)에 시세 검사를 더했습니다. 공개될 파일(`published()`, 아직 커밋하지 않은 파일 포함)에서 날짜 둘레(그 줄과 앞 한 줄, 뒤 두 줄, 앞뒤 300자 안)에 그날의 실제 가격(`data/raw/`의 시가, 고가, 저가, 종가)이 나온 짝이 2개를 넘고, 날짜가 나온 횟수의 3% 이상이면 실패입니다. 날짜는 2025-04-09, 20250409, 2025/04/09, 2025년 4월 9일, 밀리초 시각을 읽습니다. `data/raw/`가 없는 CI에서는 이 검사만 건너뛴다고 출력합니다.
  - 값만 같은 것은 세지 않습니다. 실제 가격이 수만 개라 가짜 시세와 우연히 겹치기 쉽기 때문입니다(첫 판은 이 때문에 151개 파일에서 거짓 경보).
  - 2026-11-13 시험: 손익 정답 파일(짝 18개, 날짜 393번), 들여쓴 JSON, Massive 원본 꼴, 「2025년 4월 9일」 꼴 글은 걸리고, 가짜 시세 파일(E01 골든, E04 가짜 세계: 짝 73개, 날짜 3,509번으로 2.1%), 사례, 계좌, 질문 정의 파일은 걸리지 않았습니다. 3%와 2.1%로 경계가 가깝습니다.
  - **못 잡는 것:** 실제 가격이 둘 이하인 작은 파일(예: 질문 정답 파일은 짝 2개), 날짜와 값이 300자 넘게 떨어진 표, 환율 값과 기사 글. 그래서 이 검사는 대량 유출을 잡는 그물이고, 첫 방어는 정답과 기록을 git 제외 폴더에 두는 것입니다.
- 소개 페이지는 비공개 아티팩트로 둡니다. 공개하기 전에 실제 값이 든 그림을 가짜 값 판으로 바꿉니다.

### 소개 페이지

구상 페이지와 같은 톤의 비공개 아티팩트입니다. 순서는 다른 수강생 발표 셋이 공통으로 쓴 흐름을 따릅니다.

1. 가상의 고객 요구: 정정과 취소가 와도 잔고와 손익이 원천과 1원까지 맞아야 함
2. 요구를 기술 키워드로: CDC, 현재 상태 MERGE, 증분과 재시도, 유지보수, 주기 실행
3. 아키텍처 그림과 데이터 흐름
4. 데이터: 원천 네 테이블(합성), 실제 시세와 환율, 기사와 일정
5. 기술 과제 셋과 해결: 수정과 삭제를 빠짐없이(LSN과 버전 가드), 바뀐 것만 고쳐도 같은 답(영향 키와 저장 순서), 멈췄다 살아나도 중복 없이(checkpoint와 재시도). 숫자는 모두 보고서의 실제 값
6. 화면 시연: 10번 칸(파이프라인 상태)부터 2 ~ 9번 칸까지 실제 화면 캡처
7. AI 실험: 기준을 먼저 고정한 사이클, 통과와 실패를 그대로
8. 한계와 다음: 클라우드로 옮기기, 데이터 규모, 통과하지 못한 지표

5. **저장한 매매가 없으면 예시로 시작합니다.** QQQ 세 줄(날짜, 구분, 수량만. 가격 없음)이고, 고치면 그 종목의 매매로 저장됩니다.

8. **손익 SQL의 범위를 넘는 금액은 400으로 돌려줍니다.** 손익 SQL은 수량, 체결가, 환율을 decimal로 곱해 매매 한 건이나 기준일 평가액이 약 100억 원을 넘으면 넘칩니다(미국 종목에 원화 체결가를 넣는 실수가 이렇게 됨). 서버가 이 오류를 `AMOUNT_TOO_LARGE`와 금액이 가장 큰 줄 번호로 바꾸고, 화면은 그 줄에 「단위를 확인하세요」를 표시합니다. SQL의 자료형을 넓히는 일은 손익 SQL(E01) 쪽 일이라 이번 범위 밖입니다. 체결가 칸 머리에는 종목 통화(달러, 원)를 적습니다.

1. **보일 값의 자리는 서버가 정합니다.** 범위 %는 소수 둘째 자리, 적중률은 소수 첫째 자리로 서버가 반올림해 주고, 화면은 모자란 0만 붙입니다(4단계 정한 것 1번과 같은 규칙).
2. **범위는 매매와 따로 부릅니다**(`GET /api/range`). 종목과 기준일로만 정해지므로 매매가 없어도 보이고, 매매를 고쳐도 다시 부르지 않습니다.
3. **알림과 표본 문구는 2절의 문장을 씁니다.** 70 ~ 90% 밖이면 「적중률이 70 ~ 90% 밖이라, 이 종목에서는 80% 범위가 지난날과 잘 맞지 않았습니다」, n이 20보다 작으면 「표본이 적어(n = ○) 적중률로 판단하기 어렵습니다」. 범위 숫자는 이익과 손실이 아니라 빨강과 파랑을 쓰지 않습니다.
4. **서버가 떠난 연결에 답을 쓰다 실패해도 조용히 넘깁니다.** 화면이 요청을 취소하거나 창을 닫으면 생기는 일이라, 오류 기록을 남기지 않습니다.
5. **적중률 문장에 「데이터가 2년뿐이라 참고로만 보는 값입니다」를 붙입니다**(2절 8번 칸). n = 23에서도 판정이 아니라 참고라는 것을 밝힙니다.
6. **알림은 어느 쪽으로 벗어났는지 나눠 적습니다.** 서버가 `side`를 주고, 90%를 넘으면 「80% 범위가 지난날의 움직임보다 넓었습니다」, 70%에 못 미치면 「좁았습니다」입니다. 전에는 「적중률 91.3%」 바로 아래 「잘 맞지 않았습니다」가 붙어 모순처럼 읽혔습니다. 지난 창이 0개면 표본 문구를 숨깁니다(적중률 문장이 이미 말함).
7. **보일 값의 반올림은 0.5를 0에서 먼 쪽으로 올립니다**(손익 %와 같음). 파이썬 `round`는 짝수 쪽으로 보내 13/16 = 81.25%가 81.2%가 되었습니다. 적중률은 맞은 수와 n의 정수로 셉니다.
8. **8번 칸 제목은 h2이고, 범위 문장들은 상태 알림 영역(`role="status"`)에 둡니다.** 종목을 바꿀 때 8번 칸을 잠깐 숨기는 것은 그대로 둡니다. 종목을 바꾸면 결과 칸도 숨기므로 매매 칸은 어차피 움직이고, 범위는 수십 ms 안에 다시 뜹니다.

### Spark 손익 마트 (2026-11-18, 1안 셋째)

### 화면 서버가 새 파일을 다시 읽음 (2026-11-18)

담당자가 고른 일입니다(11/18 「1안 표본, 서버」). Airflow의 `screen_export`가 새 화면 파일을 써도 켜 둔 계산 서버는 켤 때 읽은 데이터로 답하던 빈칸을 메웁니다.

- 서버(`ai/screen_server.py`)는 요청마다 화면 파일의 inode, 수정 시각, 크기를 봅니다. 바뀌었으면 그 요청에서 한 번 다시 읽고, 다른 요청이 다시 읽는 중이면 기다리지 않고 지금 데이터로 답합니다. 계산 준비(2 ~ 3초)는 뒤에서 돌립니다.
- 새 파일의 검사가 실패하면 화면은 숫자 대신 실패 항목을 보이고(손익 API 503), 파일을 읽지 못하면 「화면 파일을 다시 읽지 못함」을 실패로 둡니다. 옛 숫자를 계속 보이지 않습니다. 상태 API에 다시 읽은 횟수와 때(`reloads`, `reloaded_at`)를 더했습니다.
- 막힌 곳: DuckDB는 한 프로세스 안에서 같은 경로를 이미 열어 둔 연결이 있으면, 파일이 바뀌어도 새로 연 연결에 예전 내용을 돌려줍니다(작은 시험에서 옛 1, 하드 링크 경로로 열면 새 2). 첫 시험에서 깬 파일과 읽을 수 없는 파일로 바꿔도 「통과」로 다시 읽은 까닭입니다. 그래서 다시 읽을 때는 새 파일을 하드 링크(`.screen.reload-<프로세스>-<번호>.duckdb`, git 제외 폴더)로 걸어 그 경로로 열고, 옛 데이터와 연결은 쓰던 요청이 끝나도록 다음 다시 읽기 때 닫고 링크를 지웁니다. 끝난 서버가 남긴 링크는 다음에 켤 때 지웁니다.
- 시험(`eval/f_screen/check_api.py pipeline`): 서버를 켠 채 좋은 파일 → 내보낸 뒤 깬 파일 → 좋은 파일 → 읽을 수 없는 파일로 바꾸며 상태와 손익 API를 봅니다. 4/4(다시 읽은 횟수 0, 1, 2, 3, 깬 파일은 「내보낸 뒤 바뀌지 않음(지문)」, 읽을 수 없는 파일은 「화면 파일을 다시 읽지 못함」), 끝난 뒤 남은 링크 없음.
- 화면은 켤 때와 손익 API가 실패할 때 상태를 읽으므로, 데이터 탭의 내보낸 때는 화면을 새로 고치면 새 파일 기준으로 바뀝니다. 서버를 다시 켤 필요는 없습니다.

### 증권사와 지금 잔고 (2026-11-19, 중간 판 의견)

담당자가 11/19 중간 판에서 실제 매매를 넣어 보고 짚은 두 가지입니다(「1안 화면과 파이프라인」). 결정 기록 [0013](../decisions/0013-screen-accounts-and-transfer-in.md). 2절의 입력 정의(잠김)는 고치지 않고 칸을 더한 것이라 여기에 적습니다.

- 짚은 것: (1) 한 종목을 두 증권사에서 사고팔면 앱마다 평균 단가와 수익률이 따로인데 화면은 합친 평단 하나라, 증권사 앱의 「수익률」과 견줄 숫자가 없었습니다. 화면의 「단순 수익률」은 판 것까지 합친 손익을 넣은 돈 전체로 나눈 값이고, 앱의 수익률은 남은 주식의 평가 손익을 남은 매입 금액으로 나눈 값입니다. (2) 시세 2년 전에 사서 지금도 가진 주식은 기간 전 매수가 빠지고 그 뒤 매도가 초과 매도로 빠져 손익이 비었습니다.
- 증권사 칸: 매매 줄마다 증권사(고르지 않아도 됨, 목록은 `ai/holdings.py` BROKERS). 증권사마다 손익 SQL을 따로 돌려 평단, 실현과 평가, 매도별 손익, 남은 주식 수익률을 내고, 모든 매매를 합쳐 한 번 더 돌려 날마다의 누적 손익, SPY 선, 연 환산을 냅니다. 계좌별 장부에서 빠진 줄(계좌에 없는 수량을 판 줄)은 합친 계산에서도 빼서 두 길의 합계가 같습니다. 요약 탭에 「증권사별」 카드(큰 숫자가 남은 주식 수익률), 내 보유 줄에 남은 주식 수익률(한 계좌일 때), 매도별 손익에 증권사 이름. 증권사가 둘이면 가격 그림의 평균 단가 선은 그리지 않습니다.
- 지금 잔고 줄: 구분 「지금 잔고」에 앱 잔고 화면의 수량, 평균 단가, 평균 매입 환율(미국 종목). 같은 증권사의 기간 안 매매를 장부 규칙 그대로 거꾸로 되짚어 데이터 첫날의 보유를 셈하고, 그 원가로 첫날 산 줄을 장부 맨 앞에 넣습니다(앱 잔고는 분할을 이미 반영). 기간 전 줄은 지금처럼 OUT_OF_DATA_RANGE로 빠지고 「지금 잔고 줄이 대신해요」 안내가 붙습니다. 셀 수 없는 경우(잔고가 기간 안 매수보다 적음, 모두 판 매도 앞의 평단을 모름, 원가가 0 이하)와 기간 안 매매로 모두 설명되는 경우, 평단 차이(한 주에 0.01보다 큼)는 「계산 안내」로 알립니다. 잠긴 입력 경고(`warnings.json`)와 따로 둡니다.
- 시작 보유가 있으면 SPY 비교, SPY 선, 연 환산 수익률은 세지 않습니다(언제 얼마의 돈으로 샀는지 모름). 묻고 답하기(9번 칸)는 시작 보유와 매매를 합친 한 계좌로 셉니다.
- 레이크: 증권사마다 원천 계좌 `A-SCREEN-<코드>`, 시작 보유는 입고 주문(`TRANSFER_IN`, 899000000대), 잔고와 Gold 대조는 계좌 x 종목. 원천 제약 변경은 `make source-migrate`(0013). 11/19 Airflow DAG로 시험 매매 파일(계좌 넷, 입고 1건)을 끝까지 돌려 Gold 체결 7/7, 다시 센 손익 4/4, Gold 손익 마트 4/4(계좌, 종목) 칸마다 같음. 입고 체결은 그 계좌 장부의 맨 앞. 이어 저장 매매로 되돌릴 때, 모든 줄이 계산에서 빠진 종목(기간 전 매수와 초과 매도뿐)은 원천과 Gold에 행이 없는데 대조가 화면의 빈 요약과 견줘 실패했습니다(전부터 있던 빈칸). 체결이 없는 계좌, 종목은 견주지 않고 따로 세게 고쳤습니다.
- 담당자의 실제 매매로 화면에서 확인했습니다(종목, 증권사, 값은 공개 저장소에 남기지 않음). 계좌를 나누자 한 계좌의 남은 주식 수익률이 합친 평단일 때와 몇 %p 달라졌고, 두 계좌 손익 합은 합친 계산과 원 단위까지 같았습니다. 앱 숫자와 남은 차이는 화면 시세가 마지막 날(11/12)까지라 생기는 것으로 보입니다(해석).
- 같은 날 고친 것: 설명 시트를 여는 단추(「이 화면은」, 「계산법」, 「이 칸은」, 「답하는 법」)를 밑줄 글자에서 회색 알약과 i 아이콘으로(담당자 「밑줄이 별로」).
- 시험: `eval/f_screen/check_api.py accounts` 27/27(`make check-screen`에 들어 있음), `loaders/screen_trades.py --selftest` 18/18, 골든 30/30, 화면 값 대조 20/20과 개발 사례 7/7(새로 A01 두 증권사, A02 지금 잔고: 증권사별 카드, 내 보유 줄, SPY 칸, 매도 표, 매매 줄, 계산 안내, 그림을 API 값과 대조, 자체 시험 49/49), 대비 68/68, 입력 흐름 9/9(자체 18/18).

### 데이터 기간 늘리기 (2026-11-19, 중간 판 의견 셋째)

증권사 앱과 화면의 수익률을 견주다 화면 데이터가 11/12에서 끝나 앱(오늘 주가)과 날짜가 다른 것이 드러났습니다. 담당자가 시세를 오늘까지 늘리기로 했습니다(「11/22까지 해」, 결정 기록 [0015](../decisions/0015-extend-data-window-keep-eval-frozen.md)). 2절과 6절(잠김)은 고치지 않았습니다. 6절 1번의 「2년」은 평가 기준의 기간으로 남고, 화면의 기간만 늘어납니다.

- 원본 구간 목록 `loaders/window.json`: 화면 데이터 기간은 구간을 이어 붙인 것이고, 내보내기(`ai/screen_data.py`)가 구간마다 원본 파일을 읽어 합칩니다. 둘째 구간 2026-11-12 ~ 2026-11-18을 적재기 `--dry-run`으로 받고(국내 2종목 x 5일, 미국 17종목 x 5일 두 판, 환율 5일, 기사 3,246건) `--from-raw`로 원천에 넣었습니다(새로 97행, 겹친 날 3행은 그대로). 미국 11/12 종가는 2년치를 받던 11/13 아침에 아직 없어서 첫 구간에 빠져 있었고, 둘째 구간을 하루 겹쳐 받아 채웠습니다. Airflow 컨테이너에는 `data/`의 `raw`와 `generated`만 붙어 있어, 구간 파일은 붙어 있는 `loaders/`에 둡니다(처음 `data/`에 두었다가 DAG의 첫 태스크가 파일을 찾지 못해 한 번 다시 시도됨).
- 평가는 얼린 파일로: 정답과 견주는 시험은 11/18에 내보낸 2년치 화면 파일의 사본(`data/generated/screen_eval.duckdb`)을 `screen_data.eval_db()`로 엽니다. 내용 지문이 고정한 값과 같아야 열리고, 잃으면 `make screen-eval-data`가 첫 구간 원본에서 다시 만듭니다(다시 만든 지문이 11/18 파일과 같음을 확인). 화면 서버와 Airflow는 늘린 파일(`screen.duckdb`)을 씁니다.
- 내보내기 검사 둘을 더함(10번 칸): 「원본 구간이 겹치는 날(같은 값)」, 「평가용 파일과 같은 날(2026-11-12까지)」(늦게 나온 행을 더한 것만 허용). 11/19 DAG: 태스크 일곱 성공, 레이크 경로 시세 9,565 / 9,565행과 환율 492 / 492일 같음, 기간 2024-11-13 ~ 2026-11-18, 겹치는 날 3개 같음, 평가용 파일과 9,960개 같음과 더한 행 17(미국 11/12), `dbt build` 95/95.
- Gold 손익 마트 대조: Gold의 기준일은 데이터 끝날(11/18)이라 저장한 기준일(11/12)과 달라 4곳을 건너뛰었습니다(0/0). 화면 쪽을 Gold 기준일로 다시 세어 견주게 고쳐 4/4(두 기준일 사이 매매로 장부에 드는 줄이 달라지면 건너뜀으로 따로 셈).
- 화면: 저장한 종목은 저장 때의 기준일로 열립니다. 기준일이 데이터 끝날보다 앞이면 기준일 칸 아래에 「최신 11/18로」 단추를 보이고, 누르면 끝날로 옮겨 다시 셉니다(저장 파일 형식은 그대로).
- 담당자 확인: 담당자의 실제 매매를 늘린 끝날 종가로 세자, 장이 열리기 전에 본 증권사 앱의 「수익률」(남은 주식)과 0.01%p 차이였습니다. 전의 차이는 날짜 때문이었습니다.
