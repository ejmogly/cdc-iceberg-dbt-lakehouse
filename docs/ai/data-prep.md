이 저장소의 기본 profile(`postgres:16.15`, Debezium 커넥터 RUNNING)에서 DDL과 적재기를 그대로 돌렸습니다. 볼륨이 3회차 것이라 `infra/postgres/init/`가 다시 돌지 않아, DDL 20과 30은 10절 명령으로 실행했습니다.

| DDL 20, 30 | 오류 없음 | 오류 없음. 테이블 넷이 생김 |

## 3. 데이터에서 본 것

값은 보지 않고 행 수와 날짜만 셌습니다.

- **수정주가:** 최근 1년은 17종목 모두 `adjusted=true`와 `false`가 같았습니다(그 기간에 액면분할이 없었다는 뜻). 고르는 것은 앞으로의 분할에 대한 결정입니다(5절).
- **거래량에 소수가 섞여 옵니다:** 미국 4,250행 가운데 3,094행. `volume`은 `bigint`라 반올림해 넣습니다.
- **거래일 수가 셋 다 다릅니다:** 미국 250일, 국내 243일, ECOS 환율 245일. 국내 시세가 없고 환율만 있는 날은 2025-12-31(연말 휴장) 하루입니다.
- **미국 거래일 250일 가운데 12일(4.8%)은 같은 날짜의 ECOS 환율이 없습니다**(한국 휴일): 2026-02-17, 02-18, 03-02, 05-01, 05-05, 06-03, 07-17, 08-17, 09-24, 09-25, 10-05, 10-09. 지금 규칙(R04)은 이날 직전 값을 씁니다.
- 미국 거래일 다음 날(한국 날짜)에 환율이 없는 날은 59일(23.6%)입니다. 금요일 장의 다음 날이 토요일이라서입니다(4절 후보 B).
- 국내 거래일은 모두 같은 날짜의 환율이 있습니다.
- 종목 감성 값은 `positive`, `neutral`, `negative` 말고 `mixed`가 1건 있었습니다. DDL은 값을 막지 않습니다.

## 4. 환율 기준일 규칙 후보 (정하지 않음)

미국 거래일 t의 정규장은 한국 시각으로 t일 밤 23:30 ~ t+1일 새벽 06:00(서머타임 중에는 한 시간 이름)입니다. ECOS의 매매기준율은 한국 날짜로 고시됩니다(전 영업일 거래로 정해 그날 아침에 고시하는 값으로 알려져 있으나, 고시 시각은 이 저장소에서 확인하지 않았습니다). 그래서 "미국 t일 매매에 어느 날의 환율을 쓰나"가 손익의 첫 함정입니다. 체결 환율(`executions.fx_rate`)이 있으면 그 값을 쓰고(R03), 아래는 비었을 때의 규칙입니다.

| 후보 | 규칙 | 장점 | 단점 |
|---|---|---|---|
| A(지금 E01 R04) | 같은 날짜 t의 기준율. 없으면 직전 값 | 단순하고 재현됨. E01 골든 30개와 같은 규칙. 미국 장이 열리는 t일 밤에 이미 고시된 값이라 미래 정보가 아님 | 미국 장중 환율과 하루 가까이 어긋날 수 있음. 1년에 12일(4.8%)은 직전 값 |
| B | 다음 한국 날짜 t+1의 기준율. 없으면 그다음 값 | 미국 장이 끝나는 한국 날짜와 맞음. 실제 환전 정산과 가까울 수 있음(확인 필요) | 23.6%가 다음 날 값이 없어 며칠 뒤 값을 씀. 가장 최근 거래일은 다음 날 아침까지 계산이 안 됨. 뒤의 값을 당겨 쓰므로 D(유사 국면)의 미래 정보 막기와 부딪힘 |
| C | 미국 장 마감 시각에 이미 나와 있던 마지막 값(시각으로 as-of 조인) | "그때 알 수 있던 값"이라는 뜻이 분명 | 고시 시각 자료가 따로 필요. 아침 고시라면 결과는 A와 거의 같음 |
| D | 다른 환율 계열(서울 외환시장 종가 같은, 미국 장에 더 가까운 시각의 값) | 시차가 줄어듦 | ECOS에 어떤 일별 계열이 있는지, 언제부터 있는지 아직 확인하지 않음. 계열을 바꾸면 기간이 짧아질 수 있음 |

- A 말고 다른 것을 고르면 E01의 R04가 바뀌므로, E01 3절 변경 기록에 날짜와 이유를 남기고 골든 사례(특히 G22, G23, G25)를 다시 봐야 합니다.
- 어느 쪽이든 Gold에서 한 곳(`pnl_fx`를 만드는 staging 모델)에서만 정하면 SQL의 나머지는 그대로입니다.

## 5. 미국 수정주가 선택지 (정하지 않음)

| 선택 | 장점 | 단점 |
|---|---|---|
| `adjusted=false`(그날의 실제 가격) | 체결가(`exec_price`)와 같은 기준이라 손익 계산과 체결가 범위 검사(R08)가 맞음. 지난 값이 바뀌지 않음 | 분할이 생기면 그 앞뒤로 가격이 끊겨 수익률, 「오늘의 시장」 지표, 유사 국면(D)이 틀어짐 |
| `adjusted=true`(분할 반영) | 수익률이 이어짐 | 분할 뒤 그 전 날짜 값이 모두 바뀜(많은 `u` 이벤트, 6회차 소급 정정의 재료이기도 함). 분할 전 체결가와 맞지 않아 손익 계산에서 수량도 맞춰야 함 |
| 둘 다 | 원래 가격은 `daily_prices`, 분할은 따로 받아(Massive의 분할 정보) Gold에서 수익률만 보정 | 테이블과 적재기가 하나 늘어남 |

- 두 판 모두 분배금과 배당은 반영하지 않으므로 수익률은 가격 수익률입니다(`data/README.md`).
- 정한 판을 `provider` 값(예: `massive`, `massive_adj`)이나 따로 칸에 남길지도 함께 정합니다. 지금 적재기는 매번 `--adjusted`를 고르게 하고 `provider`에는 `massive`만 씁니다. 한 테이블에 두 판을 섞지 않습니다.

**추천(정하는 것은 사용자):**

1. 미국 CPI와 고용은 **FRED API**를 주 출처로 합니다. 키 하나로 과거와 앞으로의 날짜를 JSON으로 받고, 일정 조정도 반영됩니다. 키 이름만 `.env.example`에 더하고, README에 보증하지 않는다는 문구를 둡니다.
2. FOMC는 FRED로 대신할 수 없어 **연준 FOMC 일정 페이지**를 받습니다(공공 영역이라 조건이 가장 가벼움).
3. BLS ICS는 발표 시각을 대조하는 보조로만 씁니다.
4. 한국 쪽은 한국은행 결정회의 페이지(금리)와 국가데이터처 보도계획(물가)을 쓰되, 한국은행 자료는 출처 표시와 재배포 협의 조건이 있어 지금처럼 받는 코드만 둡니다.
5. 시각이 중요합니다. FOMC 발표(미국 동부 14:00)는 한국 시각으로 다음 날 새벽이라, 한국 종목과 맞출 때는 하루 뒤의 일로 봐야 합니다. 일정 테이블에 날짜와 함께 현지 시각과 시간대를 둡니다.

## 7. 손익 SQL 검증 (E01 골든 30개)

E01의 규칙 R01 ~ R15를 dbt 모델 모양의 SQL 11개로 옮기고, 골든 사례 30개를 DuckDB 2.0.0에서 돌려 정답과 맞췄습니다. 자세한 것은 [`sql/pnl/README.md`](../../sql/pnl/README.md)입니다.

| 확인 | 통과선(E01 3절) | 결과 |
|---|---|---|
| 숫자 일치(정답 칸과 매도 한 건씩) | 30개 전부 | 30/30 |
| 연 환산 | 0.05%p 안 | 50칸 모두, 가장 큰 차이 0.01%p |
| 항등식 | 0.01원 미만 | 30/30, 가장 큰 차이 2.3e-10원 |
| 경고 | 전부 | 30/30 |
| 입력 순서 섞기 | 30개 모두 | 30/30(사례마다 5번) |
| 다시 실행 | 같음 | 같음 |

- 첫 실행에서는 6개가 어긋났습니다. 모두 SQL 쪽 문제(달러 현지 손익의 소수가 CASE 자료형 합치기로 잘림)였고, 고친 뒤 30개가 맞았습니다. 정답과 평가 기준은 그대로입니다.
- 이것은 E01 4절의 "Python 계산기"나 "dbt 모델" 본 실행이 아닙니다. 5회차에 dbt와 Spark로 옮긴 뒤 같은 30개로 다시 돌려 E01 5절 표를 채웁니다.
- 합성 체결 10만 건(계산 단위 5,000개)으로 돌려 보니 DuckDB에서 장부(재귀 CTE) 한 번에 약 10초였습니다. Spark에서 재귀 CTE가 되는지는 5회차 버전을 정할 때 먼저 확인합니다.

## 8. CDC에 미치는 것

- 새 테이블 넷이 `source` 스키마에 있어 `cdc_pub`(`FOR TABLES IN SCHEMA source`)과 커넥터(`schema.include.list=source`)에 저절로 들어갑니다. 행이 들어오면 `src.source.fx_rates`, `src.source.attention_daily`, `src.source.news_items`, `src.source.news_ticker_sentiment` 토픽이 생깁니다.
- 처음 1년치를 넣으면 `c` 이벤트가 시세 4,736개, 환율 245개 한꺼번에 갑니다. 그 뒤로는 매일 바뀐 행만 갑니다.
- 새 테이블은 지우지 않으므로 `REPLICA IDENTITY`는 기본값으로 둡니다.
- `news_items`의 `text[]` 칸이 Debezium과 Bronze에서 어떤 모양이 되는지는 아직 보지 않았습니다(4회차에 볼 것).

PostgreSQL에서 확인할 때(기본 profile의 postgres가 떠 있을 때): 새 볼륨이면 DDL이 처음 띄울 때 만들어집니다. 기존 볼륨이면 아래 DDL을 실행합니다. 그다음 같은 적재기를 `--from-raw`로 두 번 돌려 두 번째에 "고침 0"인지 봅니다. 원본 파일 이름의 기간과 맞도록 `--start`, `--end`를 줍니다(2026-11-12에는 `--start 2025-11-12 --end 2026-11-11`).

```bash
docker compose exec -T postgres \
  psql -U app -d source_db \
  < infra/postgres/init/20_fx_rates.sql
docker compose exec -T postgres \
  psql -U app -d source_db \
  < infra/postgres/init/30_attention_news.sql
```

`app`, `source_db`는 `.env`의 `POSTGRES_USER`, `POSTGRES_DB` 값으로 바꿉니다.
