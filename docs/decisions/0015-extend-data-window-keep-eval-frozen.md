# 0015 데이터 기간은 원본 구간을 뒤에 더해 늘리고, 평가는 정답을 고정한 때의 얼린 파일로 한다

- 날짜: 2026-11-19
- 상태: 결정(담당자 「11/22까지 해」), 확인함. 구간 목록의 자리와 늘리는 방법은 [0016](0016-window-extend-fetch-on-mac-process-in-airflow.md)에서 바뀜

## 맥락

화면 데이터는 2024-11-13 ~ 2026-11-12(2년)에서 끝났습니다. 11/19 중간 판에서 담당자가 증권사 앱의 수익률과 화면을 견줬을 때, 앱은 오늘 주가로, 화면은 11/12 종가로 세어 차이가 났습니다(두 계좌 모두 같은 쪽으로 같은 크기만큼 달라 계산 방식의 차이는 아니었음). 담당자는 시세를 오늘까지 늘리는 일을 11/22까지 하기로 했습니다.

걸리는 것이 셋 있었습니다.

1. 평가 기준이 이 2년에 묶여 있습니다. 2년치 원본 파일(`data/raw/`)의 sha256이 `eval/f_screen/lock.json`에 있고, 실제 데이터 사례의 정답(`expected_real.json` 등)은 이 원본으로 셌습니다.
2. 미국 시세는 2년치를 받던 때(11/13 아침) 11/12 종가가 아직 나오지 않아 11/11에서 끝났습니다. 11/12 종가를 더하면 기준일이 11/12인 국내 사례 셋(R01, R02, R12)의 SPY 비교값이 바뀝니다(손익 SQL은 그날 SPY 종가가 없을 때만 직전 값을 씀).
3. 데이터 기간의 끝(`2026-11-12`)이 내보내기 코드에 상수로 박혀 있었고, 원본 파일 이름도 그 기간 하나로만 찾았습니다.

## 결정

1. **원본 구간 목록**: 화면 데이터 기간은 `loaders/window.json`의 구간을 이어 붙인 것입니다. 첫 구간(2년치)은 그대로 두고, 늘릴 때는 적재기를 `--start`, `--end`로 돌려 받은 새 구간 파일을 뒤에 더합니다. 새 구간은 앞 구간의 끝날부터 하루 겹쳐 받습니다(늦게 나온 종가를 받으려고). 겹치는 날은 원본끼리 값이 같아야 하고, 내보낼 때 검사합니다(「원본 구간이 겹치는 날」).
2. **평가는 얼린 파일로**: 정답과 견주는 시험(`check_api`, `check_screen`, `check_range`, `check_flows`, `check_qa`, `run_qa`, E02의 `run`, `pool`, `judge_answers`, `make_cites`)은 `data/generated/screen_eval.duckdb`를 엽니다(`ai.screen_data.eval_db()`). 11/18에 내보낸 2년치 화면 파일의 사본이고, 내용 테이블의 지문(`EVAL_DIGEST`)이 같아야 열립니다. 잃으면 `make screen-eval-data`가 첫 구간 원본에서 다시 만듭니다(지문이 같아야 바꿈).
3. **늘린 파일의 지난 값 대조**: 내보낼 때 EVAL_END(2026-11-12)까지의 시세와 환율이 평가용 파일과 같은지 봅니다(「평가용 파일과 같은 날」). 평가용 파일에 없던 행(미국 11/12 종가)을 더한 것만 허용하고, 값이 바뀌거나 빠지면 검사가 실패해 화면이 숫자 대신 실패 항목을 보입니다.
4. **화면 서버와 레이크**는 늘린 파일(`screen.duckdb`)을 씁니다. 새 구간 시세와 환율은 원천 PostgreSQL에 넣어 CDC로 Bronze, Silver, Gold까지 가고, Gold 마트에서 내보냅니다(지금과 같은 길).

## 영향

- 잠긴 파일(평가 기준 문서의 절, 정답, 2년치 원본, `lock.json`)은 고치지 않습니다. 평가 결과는 같은 데이터로 재므로 바뀌지 않습니다.
- 화면의 데이터 기간은 2년보다 조금 길어집니다(시작은 2024-11-13 그대로). 설계서 6절 1번의 「2년」은 평가 기준의 기간으로 남습니다.
- 화면의 기준일 기본값이 늘린 끝날로 바뀝니다. 저장한 매매의 기준일은 저장한 값 그대로이고, 그 기준일이 끝날보다 앞이면 기준일 칸 아래에 「최신 <끝날>로」 단추가 보입니다.
- Gold 손익 마트의 기준일은 데이터 끝날이라 저장한 기준일과 달라집니다. `loaders/screen_trades.py --verify`는 화면 쪽을 Gold 기준일로 다시 세어 견줍니다(두 기준일 사이 매매로 장부에 드는 줄이 달라지면 건너뜀으로 따로 셈).
- 다음에 늘릴 때는 `make window-extend`(`loaders/extend_window.py`)가 받기, 원천 적재, 구간 더하기를 하고 `make lake-refresh`가 나머지를 합니다. 11/19에 받기는 Mac, 나머지는 Airflow DAG `window_extend`로 바꿨고, 구간 목록은 `data/generated/window.json`으로 옮겼습니다(0016).

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
|---|---|
| 2년치 원본을 새 기간으로 다시 받아 바꿈 | 잠근 원본 지문이 깨지고, 정답을 다시 세야 함 |
| 새 구간을 11/13부터 받아 미국 11/12를 빼 둠 | 실제 거래일 하루가 영영 비고, 그날 매매는 직전 종가로 셈 |
| 평가도 늘린 파일로 하고 바뀐 사례만 다시 셈 | 정답을 본 뒤 고치는 일이 되어 0009(평가를 개발 전에 고정)에 어긋남 |
| 기간을 2년으로 굴림(시작도 뒤로) | 첫날 앞의 매매가 계산에서 빠지는 사례가 생기고 정답과 어긋남 |
