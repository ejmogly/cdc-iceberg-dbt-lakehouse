# 0011 Silver는 Bronze의 새 스냅샷만 읽는다

- 날짜: 2026-11-18
- 상태: 결정(담당자 「Silver 증분 읽기로」), 확인함

## 맥락

[규모 시험](../reports/2026-11-18_scale-test.md)에서 Silver MERGE가 바뀐 것이 없어도 Bronze 이력 전체를 매번 펼쳤습니다. 1단계(`1_incoming.sql`)가 `lake.bronze.<테이블>`을 통째로 읽고 검사와 최신 후보를 고르기 때문입니다. Bronze 체결이 55행에서 727,355행이 되자 바뀐 것 없는 실행이 8.7초에서 73초가 됐고, Airflow DAG 한 번이 약 3분이 됐습니다. Bronze는 원천 변경의 이력이라 지우지 않는 것이 원칙이므로, 이력이 쌓여도 Silver가 느려지지 않아야 합니다.

## 결정

1. **구간**: 테이블마다 마지막으로 읽은 Bronze 스냅샷을 `lake.silver.merge_progress`에 남깁니다. 다음 실행은 그 스냅샷(빼고)부터 지금 main의 스냅샷(넣고)까지만 읽습니다. 같으면 할 일이 없습니다.
2. **읽는 방법**: Iceberg 변경 뷰(`create_changelog_view`)의 INSERT 행만 씁니다. Bronze는 덧붙이기만 하고, 압축(`replace`) 스냅샷은 변경 뷰가 건너뛰므로 압축한 파일을 다시 읽지 않습니다. INSERT가 아닌 변경이 보이면 멈춥니다.
3. **SQL은 그대로**: `sql/silver/<테이블>/1_incoming.sql`의 `lake.bronze.<테이블>` 한 곳만 실행기([`sql/silver/run.py`](../../sql/silver/run.py))가 입력 뷰로 바꿔 끼우고, `2_merge.sql`은 그대로 돌립니다. `infra/spark/silver.sh`(전체 읽기)도 그대로 씁니다.
4. **새 행이 없으면 MERGE를 건너뜀**: Flink는 행 없는 checkpoint도 빈 스냅샷으로 남깁니다. 새 행이 0이면 MERGE 없이 progress만 옮겨, Silver에 빈 스냅샷을 만들지 않습니다(증분 Gold가 할 일 없음으로 넘어감).
5. **멈췄다 다시 돌리면**: progress는 MERGE 뒤에 저장합니다. 그 사이에 멈추면 다음 실행이 같은 구간을 다시 읽고, MERGE의 버전 가드([0010](0010-silver-current-state-rules.md) 2, 6)가 이미 반영한 변경을 거절해 답이 같습니다.
6. **비상 경로**: progress가 없거나, 시작 스냅샷이 만료됐거나, `--full`이면 끝 스냅샷의 Bronze 전체를 읽습니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
|---|---|
| Bronze 이력을 지워 가볍게 | 원천 변경의 이력을 잃음. 다시 처리하거나 감사할 근거가 사라짐 |
| `ingested_at`이나 Kafka offset으로 거르기 | 전체 파일을 열어 걸러야 해 읽는 양이 줄지 않음. 압축 뒤에도 같은 행을 다시 읽을 수 있음 |
| 시간 구간(`TIMESTAMP AS OF`) 차이 | 같은 시각의 commit 경계가 모호함. 스냅샷 번호가 정확함 |
| Spark 구조적 스트리밍으로 Bronze를 계속 읽기 | 배치 DAG 하나로 묶은 지금 구성보다 움직이는 부품이 늘어남 |

## 잃는 것

`1_incoming.sql`의 검사(봉투, 같은 전달 위치의 다른 원문, 빈 값)가 구간 안의 행에만 걸립니다. 구간을 넘는 중복 전달 위치는 증분 실행에서 보이지 않습니다. 그래서 실행기의 `--compare`(Bronze 전체로 만든 답과 Silver를 모든 칸으로 비교)와 `--full`을 남겨, 유지보수 때 한 번씩 돌립니다.

## 확인한 것 (2026-11-18)

모든 경우에 `--compare`가 다섯 테이블 모두 「Silver에만 0 / 전체에만 0」이었습니다.

| 경우 | 결과 |
|---|---|
| 첫 실행(progress 없음) | 전체 읽기, Bronze 주문 727,358행, 체결 727,355행. MERGE 61초 |
| 바뀐 것 없음 | 1.2초(빈 스냅샷만이라 MERGE 건너뜀). 전에는 Silver MERGE만 73초 |
| 매매 50건 | 테이블마다 Bronze 행 50, 1 ~ 1.5초 |
| 실행 사이에 Bronze 주문 압축(파일 104개 → 5개) 뒤 매매 30건 | 새 행 30개만 읽음 |
| MERGE 뒤 progress 저장 전에 멈춤 | 다시 돌리면 같은 구간 20행을 다시 읽고 같은 답 |
| progress 스냅샷이 없음(만료 흉내) | 그 테이블만 전체 읽기로 돌아감 |
| 합성 매매 100건 지우기 | 지움 표시로 반영 |
| Airflow DAG 한 번(바뀐 것 없음) | `silver_merge` 73.3초 → 1.6초, DAG 전체 179.5초 → 110.6초 |
