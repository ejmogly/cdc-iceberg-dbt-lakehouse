# 0009 평가 기준은 개발 전에 커밋

- 날짜: 2026-11-06
- 상태: 결정

## 맥락

AI 기능(설명, 유사 국면, 에이전트)은 만들고 나서 결과를 보면 기준을 결과에 맞추고 싶어집니다.
"잘 된다"는 말은 무엇과 비교해 얼마나 나아졌는지가 있어야 믿을 수 있습니다.

## 결정

1. 기능마다 실험 문서([`docs/ai/experiments/`](../ai/experiments/))에 문제, 가설, 평가 기준(지표, 평가셋, 통과선, 기준선)을 먼저 씁니다.
2. 평가 기준은 **개발을 시작하기 전에 커밋**합니다. 커밋한 날을 문서 머리에 적고, git 기록의 날짜가 순서의 증거가 됩니다.
3. 기준을 바꾸면 날짜와 이유를 문서에 남깁니다. 정답 파일을 결과에 맞춰 고치지 않습니다.
4. 정답은 시스템과 따로 만든 계산기나 가짜 세계에서 냅니다.
5. 숫자는 규칙으로 정확히 채점하고, 글만 판정 모델로 채점합니다. 판정 모델은 사람이 표본을 다시 봐서 일치율을 잽니다.
6. 실험 전에 데이터가 판정을 할 수 있는지(판별력)를 먼저 잽니다. 할 수 없으면 판정 데이터를 바꿉니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
|---|---|
| 만들면서 기준 정하기 | 결과에 맞춰 기준이 움직여, 나아졌는지 말할 수 없음 |
| 사람이 눈으로만 평가 | 반복할 수 없고, 손잡이(모델, 검색 개수)를 바꿔 비교할 수 없음 |
| 공개 벤치마크만 | 이 앱의 질문(나눠 산 매매, 환율, 인과 표현 금지)을 재지 못함 |

예외 둘:

1. **커밋 대신 sha256 기록(E03, E02와 F).** 까닭은 실험마다 다릅니다. E03은 기준 커밋과 백테스트 커밋이 2분 차이로 함께 들어가 git 날짜만으로는 순서가 보이지 않습니다. E02와 F는 정답과 원본이 git 밖(실제 시세, 재배포 금지)이라 커밋으로 묶을 수 없습니다. 기준을 확정한 때의 sha256과 시각을 기록 파일(`eval/e03_regime/criteria_lock.json`, `eval/f_screen/lock.json`)에 먼저 남기고, 실험 문서 머리에 순서를 밝혔습니다. 잠금 검사가 지금 파일이 그 지문과 같은지 봅니다(E02와 F는 `eval/f_screen/lock.py --verify`, E03은 `eval/e03_regime/backtest.py --verify`).
2. **판정 모델의 사람 일치율을 재지 못함(E02).** 결정 5의 사람 표본을 2026-11-20 담당자가 빼기로 했습니다(판정 모델도 Claude라 Claude가 대신 표시할 수 없음). 그래서 판정 모델 점수(recall@5, 근거 충실도)는 「사람 확인 없음, 참고값」으로 적습니다([E02](../ai/experiments/E02-rag.md) 4절).

## 결과

- 저장소를 공개할 때 git 기록을 보존해야 순서의 증거가 남습니다. 기록 없이 새로 만들면 이 주장은 증거를 잃습니다.
