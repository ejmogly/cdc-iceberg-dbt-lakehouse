# 0017 화면에 넣은 담당자의 매매를 원천으로 옮겨 레이크를 거치게 한다

- 날짜: 2026-11-18(결정과 구현, 커밋 `1209ce1`), 2026-11-24(기록)
- 상태: 결정, 확인함. 기록은 2026-11-20 독립 검토가 「결정 기록 없음」을 짚어 뒤늦게 씀

## 맥락

[0003](0003-synthetic-trades-public-prices.md)은 주문, 체결, 잔고를 합성 데이터로 정했습니다. 11/13부터 만든 화면 「내 투자 돌아보기」는 담당자가 넣은 실제 매매로 손익을 세는데, 그 매매는 레이크하우스를 거치지 않고 계산 서버가 바로 셌습니다. 담당자는 11/18 「1안」으로 화면이 레이크의 Gold를 읽고, 넣은 매매도 CDC로 Gold까지 가게 하기로 했습니다([F 설계서](../ai/F-screen.md) 7절 「내 매매도 CDC로」).

## 결정

1. 화면 저장 파일(`data/generated/f_screen/screen_trades.json`, git 밖)의 매매를 `loaders/screen_trades.py`가 원천의 주문, 체결, 잔고로 옮깁니다. 매매 한 줄이 주문 한 건과 체결 한 건이고, 체결가와 환율은 계산 서버가 쓴 값 그대로입니다.
2. 계좌는 `A-SCREEN`(증권사를 고르지 않은 줄)과 `A-SCREEN-<증권사 코드>`입니다([0013](0013-screen-accounts-and-transfer-in.md)). 시나리오 계좌 `A-0001`, 규모 시험 계좌 `A-LOAD`와 나눕니다.
3. 번호는 주문 900000000대, 체결은 그 번호 + 100000000, 입고는 899000000대입니다. 줄 순서가 같으면 번호가 같아 다시 돌려도 값이 바뀐 줄만 고칩니다.
4. Airflow DAG `lakehouse_refresh`의 첫 태스크(`trades_to_source`)가 옮기고, 마지막 태스크(`trades_verify`)가 Gold 체결과 손익 마트를 화면과 견줍니다.

## 보존과 지우는 길

- 매매 값은 이 컴퓨터의 원천 DB, Kafka 토픽, Iceberg(Bronze, Silver, Gold)에만 있고, 저장소 파일과 git 기록에는 들어가지 않습니다. 저장 파일과 대조 결과는 `data/generated/`(git 밖)입니다. 레이크의 볼륨은 이 컴퓨터 밖으로 내보내지 않습니다.
- 화면에서 줄을 지우면 원천에서 지우고, Silver는 지움 표시, Gold는 그 행이 빠집니다. Bronze는 지우지 않는 이력이라([0011](0011-silver-incremental-read.md)) 옛 값이 남습니다.
- 매매를 레이크에서 모두 없애려면 `docker compose down -v`로 원천, Kafka, 카탈로그, 레이크 볼륨을 함께 지웁니다. 그 뒤에는 시나리오와 시세를 처음부터 다시 넣어야 합니다.

## 검토한 다른 방법

| 방법 | 고르지 않은 이유 |
|---|---|
| 화면 매매는 레이크 밖에 둠(11/17까지) | 화면 숫자가 레이크를 거치지 않아, 프로젝트가 보이려는 「원천부터 Gold까지 맞는가」가 화면에는 닿지 않음 |
| 합성 매매로만 화면 시험 | 증권사 앱과 맞춰 보는 확인(0013)을 할 수 없음 |

## 영향

- 0003의 「주문, 체결, 잔고는 합성」은 이 계좌들에는 맞지 않습니다(0003 상태 줄).
- 공개 저장소에는 담당자의 실제 매매를 남기지 않습니다. 시험은 둥근 수량과 값으로 꾸민 매매 파일을 씁니다.
- 확인한 것은 F 설계서 7절 「내 매매도 CDC로」, 「Airflow로 묶기」와 0013 확인 표에 있습니다.
